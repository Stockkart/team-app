# stockkart-team-app

**Status:** Android-releasable app (screens, signer module, offline queue and sync all wired; iOS builds and passes tests, not released)

**Stockkart Team**: the Stockkart Expo / React Native app a worker signs in to, pairs with their employee record and then uses to record check-in and check-out punches after their phone's own fingerprint or face check (`.kiro/specs/HR-module`, `.kiro/specs/worker-app`). Android ships first; the same code base builds for iOS (not released in this version).

This repository holds the app alone (worker-app D17, DD21). It was `inventory-platform/apps/attendance` until D17; the web monorepo keeps the history and the web copy of the protocol package. The app is the repository root; `packages/attendance-protocol` is the app's copy of the shared protocol (`@stockkart/attendance-protocol`), kept byte-identical to `inventory-platform/platform/attendance-protocol` by `scripts/protocol-parity.mjs` (see Protocol parity).

## Signer (`src/signer`, `modules/biometric-signer`)

The only platform-specific code in the app (design DD5, R4.11, R5.12). Everything else calls the `BiometricSigner` interface:

### Key attestation (task 16.4, recorded only)

What it is for: the server trusts that a punch was made by a biometric-gated key in secure hardware because the signature verifies against the `punchPublicKey` registered at pairing. Nothing in that proves _where_ the key lives; a modified app on a rooted phone could register a software key (design, Security assumption 2). Android key attestation closes that gap: the secure hardware itself signs a description of the key (security level, algorithm, curve, which authentication unlocks it, and a challenge the server chose) into the key's certificate chain, rooted in Google's attestation root.

What the app does: `PairingFlow.agree` calls `createKeys({ attestationChallenge: utf8Bytes(claimToken) })`. On Android `SignerKeyStore` generates the punch key with `setAttestationChallenge(challenge)` and returns `KeyStore.getCertificateChain(PUNCH_ALIAS)` as `punchAttestationChain` (Base64 DER X.509, leaf first). If the key store refuses to attest (no provisioned attestation key, some vendors), it falls back to a plain hardware key and returns no chain, so attestation never blocks pairing. iOS and `FakeBiometricSigner` ignore the option and return no chain. When a chain is present `PairingFlow` adds `attestationChain` to the `complete` request; otherwise the field is omitted and the request is byte-for-byte what it was before.

What the server verifies (`KeyAttestation` in `inventory-api`): the chain to a Google Hardware Attestation Root, `attestationSecurityLevel` ∈ {TrustedEnvironment, StrongBox}, the challenge equals the claim token, and the hardware-enforced list says SIGN-only, EC P-256, strong biometric with no `noAuthRequired` and `authTimeout` ≤ 30 s, and that the attested key is the `punchPublicKey`. The verdict is stored on the pairing (`attested` true / false / null in `PairingStateResponse`) and counted; **a failed or missing attestation does not refuse the pairing**. Enforcement, and anything like Play Integrity or iOS App Attest, is a later switch.

- `packages/attendance-protocol` is pure TypeScript (no React, no fetch, no Expo); it depends on nothing in `src/`. Its `src/**` and `fixtures/**` are a byte-identical copy of the web monorepo's package (Protocol parity below).
- No `type: module` in `package.json`: Metro, Babel and Expo CLI read `metro.config.js`, `babel.config.js` and `app.config.js` as CommonJS.
- Worker-app rules in `eslint.config.mjs` (R9.2, R12.1, R12.8, R12.11): `react/jsx-no-literals` (children; `ignoreProps`) plus a `no-restricted-syntax` selector on the text-bearing props (`label`, `accessibilityLabel`, `placeholder`, …), so text reaches a screen only through `t()` from `src/i18n`; `no-restricted-syntax` on hex and `rgb(`/`rgba(` literals outside `src/theme/tokens.ts`; `no-restricted-imports` for `expo-haptics` (only `src/theme/haptics.ts`) and `@react-native-async-storage/*` (nowhere). Tests and `test-support/` are exempt from the two literal rules. The HR-module screens in `src/screens/` (Pair, Consent, the punch home, Settings) carry a per-file `eslint-disable` because the worker app reuses them as they are; History was restyled on the kit (task 20.3) and is linted like every new screen and the navigator.

## Commands

Run from the repository root. Node 22 (`.nvmrc`) and pnpm 9.8.0 through Corepack (`corepack enable && corepack prepare pnpm@9.8.0 --activate`); `pnpm install --frozen-lockfile` uses this repository's own `pnpm-lock.yaml`.

```sh
pnpm lint             # eslint . (app, test-support, packages/attendance-protocol)
pnpm typecheck        # tsc --build on tsconfig.json: tsconfig.app.json, tsconfig.spec.json and packages/attendance-protocol/tsconfig.lib.json
pnpm test             # vitest run: the app's node and jsdom projects plus packages/attendance-protocol (fixture and property tests)
pnpm check:strings    # node scripts/check-strings.mjs (strings.en.ts ↔ t('...') cross-check, R12.11)
pnpm check:protocol   # node scripts/protocol-parity.mjs (see Protocol parity)
pnpm prebuild:android # expo prebuild --platform android --no-install; then: cd android && ./gradlew assembleDebug (JDK 17 + Android SDK)
pnpm prebuild:ios     # expo prebuild --platform ios --no-install; then pod install and xcodebuild for the simulator (macOS only)

cp .env-example .env                # then edit EXPO_PUBLIC_API_URL and EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID
pnpm exec expo config --type public # resolved config (fails without an https:// API URL)
pnpm start                          # expo start
pnpm android                        # expo run:android; needs the Android SDK; the signer module is native, so Expo Go cannot run the app
pnpm eas:preview                    # eas build --profile preview --platform android
```

There is no `build` script; EAS builds the binaries that ship (`eas.json`). The two `prebuild:*` scripts exist so CI can prove the native projects generate and compile. `pnpm format` / `pnpm format:check` run Prettier (`.prettierrc`, `.prettierignore`).

## Protocol parity

`packages/attendance-protocol` and `inventory-platform/platform/attendance-protocol` are two copies of one package (worker-app D17, DD21): the web monorepo's `core/hr` imports the web copy, this app imports its own. The Java fixtures in `inventory-api` (`fixtures/phones.json`, `fixtures/canonical.json`, generated by the `core/hr` tests there) are the real contract and both copies keep their fixture tests against them; the parity script is the cheaper check on top, proving the copies have not drifted.

- `pnpm check:protocol` runs `scripts/protocol-parity.mjs` (plain Node, no dependency). It resolves `INVENTORY_PLATFORM_DIR` (default `../inventory-platform`, relative to this repository) and compares every file under `src/**` and `fixtures/**` of the two packages. Other files (`package.json`, `vite.config.mts`, `README.md`, `eslint.config.mjs`) may differ: the package name is `@stockkart/attendance-protocol` here and `@inventory-platform/attendance-protocol` there.
- Output: `protocol parity: N files identical` and exit 0; or one line per file missing on either side or differing in bytes, then exit 1. When `<dir>/platform/attendance-protocol` does not exist it prints `skip: inventory-platform not found at <dir>` and exits 0, so a clone of this repository alone still passes.
- `node --test scripts/protocol-parity.test.mjs` covers the script on temp directories (identical, one byte changed, a file missing on each side, the other repository absent).
- Order for a protocol change: the web monorepo first (`platform/attendance-protocol`, its fixture tests green, merged to `main`), then this repository (the same change in `packages/attendance-protocol`, its tests green, `pnpm check:protocol` green against the merged platform `main`). `inventory-platform` never points at this repository; the dependency is one-way.

## Live contract test (`src/contract/liveBackend.contract.test.ts`)

Runs the app's real modules against a running `inventory-api` over HTTPS, with `FakeBiometricSigner` (real P-256 keys) standing in for the phone hardware, as one suite, the worker's whole day (worker-app task 15.1, trimmed by task 19.4): `AccountClient` (Bearer) next to `AppClient` (envelope), `AuthStore`, `completeSignIn`, `AppStateMachine.resolve` run the way `useAppState` runs it, `PairingFlow` over `WorkerPairingClient` and `ownedPairingStore`, `PunchFlow`, `PunchQueue` + `SyncWorker`, `loadHistory`, `logout`, `switchAccount`, `removePhone`, `PairingStore`. It proves the canonical punch payload, the signed envelope headers, the Base64 DER signature encoding and the DTO shapes agree between the TypeScript and Java sides, through the backend's real interceptor chain. The scenario: a worker creates an account (`WORKER`, `source: worker-app`) → Join; finds the shop by the owner's e-mail → asks to join → Waiting; the manager approves with `CREATE` from `/hr/join-requests` → Home with the three modules; the manager makes a pairing code → claim / complete on `/hr/worker/pairings/*` with the login, and the phone records the account as the pairing's owner; `GET /attendance-app/me` over the envelope; log out keeps the pairing and its owner, **a punch with the session logged out is stored** (R9.10), and the same account's sign-in returns to Home with Attendance enabled and the punch on it, no question asked; replay, duplicate, an offline punch drained by the sync worker, `GET /attendance-app/punches`, `POST /attendance-app/consent`, an unknown key refused as not verified; a code made for another worker is refused word for word and still works for its owner; a request carrying both credentials is refused on either chain; signing in with a different account unpairs the phone and warns about the waiting punch, decided by the recorded owner alone; Leave this shop exits the employee today and lands on Join; Remove this phone unpairs, wipes the phone (owner included) and keeps the session.

The manager's side (sign up, register a shop, save the HR settings with the switch on, add an employee, read the inbox, approve, pairing code, read the employee) uses the Bearer endpoints with plain `fetch`, so no database access is needed.

It is **skipped** unless `ATTENDANCE_CONTRACT_URL` is set; `pnpm test` never runs it in CI. The URL must be `https://` (the client refuses anything else, R9.7); a self-signed backend certificate is trusted through Node's `NODE_EXTRA_CA_CERTS`, nothing in the app is relaxed. Recipe used at HR-module checkpoint 15 and worker-app task 15.1 (throwaway MongoDB as a single-node replica set, which the approval transaction needs, plus the packaged jar bound to a private address):

```sh
# MongoDB 7 as a one-member replica set (the worker approval runs in a transaction)
docker run -d --name contract-mongo -p 127.0.0.1:27018:27017 mongo:7 --replSet rs0 --bind_ip_all
docker exec contract-mongo mongosh --quiet --eval "rs.initiate({_id:'rs0',members:[{_id:0,host:'127.0.0.1:27017'}]})"

# backend (inventory-api): keystore with the address the test will call in its SAN
keytool -genkeypair -alias api -keyalg EC -groupname secp256r1 -dname CN=contract -ext SAN=ip:127.0.0.1 \
  -storetype PKCS12 -keystore /tmp/tls.p12 -storepass changeit
keytool -exportcert -rfc -alias api -keystore /tmp/tls.p12 -storepass changeit -file /tmp/tls-cert.pem
# every other value is a dummy (OCR, AWS, e-mail off); GOOGLE_OAUTH_CLIENT_IDS must be non-empty because
# the Google verifier fails closed without it, even though the test never signs in with Google
DB_URI='mongodb://127.0.0.1:27018/contract?directConnection=true' CLIENT_URL=https://localhost \
  GOOGLE_OAUTH_CLIENT_IDS=contract-test-client-id.apps.googleusercontent.com MESSAGING_EMAIL_ENABLED=false ... \
  java -jar app/target/app-1.0.0.jar --server.address=127.0.0.1 --server.port=8443 --server.ssl.enabled=true \
  --server.ssl.key-store=/tmp/tls.p12 --server.ssl.key-store-password=changeit --server.ssl.key-store-type=PKCS12

# app (from the stockkart-team-app repository root)
NODE_EXTRA_CA_CERTS=/tmp/tls-cert.pem ATTENDANCE_CONTRACT_URL=https://127.0.0.1:8443/api/v1 \
  pnpm exec vitest run src/contract/
```

The suite signs up a fresh owner and shop (`contract-<stamp>@example.invalid`) and its own worker accounts, so a run needs no cleanup on a throwaway database and must not be pointed at a real one. Stop the jar and remove the container afterwards. When the app's tests run inside the dev container and the jar on the host, bind the jar to the docker bridge address of the container's network instead of `127.0.0.1`, put that address in the certificate's SAN, and copy the PEM into the container for `NODE_EXTRA_CA_CERTS`.

## Testing on an emulator against a local HTTPS proxy

`plugins/withDebugUserCaTrust.js` makes **debug** builds trust CA certificates installed by the
tester on the device (release builds trust only the system store). That lets an Android emulator
reach a backend behind a local proxy with a private certificate, e.g. Caddy with `tls internal`
on the host (`https://10.0.2.2:8443` from the emulator). Install the proxy's root CA on the
emulator first (Settings → Security → More security settings → Install from device storage → CA
certificate). Cleartext HTTP stays forbidden in every variant (R9.7).

**Emulator note.** The Android emulator's key store is software-backed, so pairing on it fails
with "This phone has no secure hardware" (R5.1). `SignerKeyStore` relaxes that rule only when the
host app is a _debuggable_ build **and** the device is an emulator (both detected natively); a debug
build on a real phone, and every release build, still require secure hardware.
